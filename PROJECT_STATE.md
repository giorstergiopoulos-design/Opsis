## DeskZones edge-stretch — REAL root cause found and fixed (2026-09-30)
User tested the earlier `AdjustForInvisibleFrame` fix themselves and reported it was still wrong: "παραμένει κενό ανάμεσα στο παράθυρο και την άκρη" (a gap remains between the window and the edge). Re-investigated instead of assuming the earlier fix was sufficient.

Error:
Even with a mathematically-correct DWM invisible-frame compensation, a window snapped to an edge-touching zone still stopped short of the true screen edge by a small, constant margin.

Cause:
The REAL bug was upstream in `ZoneLayoutStore.BuildTemplate`, not in `ZoneSnapEngine` at all. Every loop-generated template (Columns/Rows/Grid/Custom) applied `gap/2` (a deliberate small visual gap between adjacent zones, like real FancyZones) **symmetrically to all four sides of every zone** — including the outer sides that touch the actual screen edge (X=0, Y=0, right=1, bottom=1), where there is no neighboring zone to justify a gap. Confirmed exactly against the user's own saved layout: a 2-row "Rows" template produced `Y: 0.006 / Height: 0.488` for the top row and `Y: 0.506 / Height: 0.488` for the bottom row — top zone starts 0.6% short of Y=0, bottom zone ends 0.6% short of Y=1, on EVERY screen resolution, regardless of `AdjustForInvisibleFrame` being perfectly correct (it can only stretch the window to match the zone it's given — and the zone itself never reached the edge).

Fix:
Rewrote `BuildTemplate`'s cell-range math (new `CellRange` local helper) so `gap/2` is applied **only on internal grid lines** — the first cell's start and the last cell's end are pinned exactly to 0.0/1.0 with zero padding — for Columns, Rows, and Grid/Custom. ("Priority Grid" was already hand-written with explicit 0/1 anchors and never had this bug; "Focus" intentionally keeps its 10% centered margin — not edge-touching by design.) Also directly migrated the user's existing saved `zonelayouts.json` (their live 2-row layout) to the corrected values (`Y:0/Height:0.494` and `Y:0.506/Height:0.494`) so the fix applies immediately without needing to redo their setup.

Affected files:
`src/Widgets/ZoneLayoutStore.cs` (`BuildTemplate`), `%AppData%\MotionDeskStudio\zonelayouts.json` (data migration, this machine only).

Prevention:
When generating any fractional/normalized layout grid, edge cells must never receive outer padding meant for inter-cell gaps — always special-case index 0 and index count-1 per axis.

Status: DONE, build clean. Root cause confirmed via direct arithmetic match against the user's own pre-existing (buggy) saved data.

## DeskZones snap engine rework (2026-09-30, same day) — user still reported "δεν λειτουργεί" after the zone-geometry fix
User pushed back again after manually testing: real Shift+drag still didn't snap, AND the overlay looked "too intense" (like a solid block) instead of translucent. Asked to research the real FancyZones (PowerToys, GitHub) architecture and reverse-engineer the *technique* (not copy code — user explicitly flagged copyright; confirmed clean-room: only identified which public Win32 API they call, wrote fully original C#).

Root cause #1 (why snapping itself was unreliable):
`ZoneSnapEngine`'s previous implementation detected "a window drag started" with its own heuristic on top of a raw `WH_MOUSE_LL` low-level mouse hook (left-button-down on a `WS_CAPTION` window, then >6px movement = "dragging"). This is NOT the same signal Windows itself uses to know a window actually entered its native move/size loop, and proved unreliable both for the user's real usage and for scripted verification (a synthetic drag visibly moved a test window but never triggered the old hook's snap logic).

Fix:
Pulled `microsoft/PowerToys` `FancyZones.cpp` via `gh api` **only to identify the technique**, then deleted the file and wrote independent C#. Real FancyZones uses `SetWinEventHook` with `EVENT_SYSTEM_MOVESIZESTART`/`EVENT_SYSTEM_MOVESIZEEND` — a documented, public Windows accessibility API that fires the OS's own authoritative signal for "a window just entered/exited its native move-or-resize loop." Rewrote `ZoneSnapEngine.cs` around this: `SetWinEventHook(EVENT_SYSTEM_MOVESIZESTART, EVENT_SYSTEM_MOVESIZEEND, ..., WINEVENT_OUTOFCONTEXT | WINEVENT_SKIPOWNPROCESS)` (the `SKIPOWNPROCESS` flag also auto-excludes MotionDesk's own widgets — no more manual pid filtering needed). On start: begin a 16ms poll timer tracking cursor position for the overlay/highlight. On end: commit the snap (via the existing, already-correct `AdjustForInvisibleFrame`) if Shift is still held and a zone is highlighted. Simplified `IsCandidateWindow` (dropped the `WS_CAPTION`/`WS_EX_TOOLWINDOW` style checks — the MOVESIZESTART event is already authoritative, and the old style checks could silently reject modern custom-titlebar apps).

Root cause #2 (why the overlay looked "too intense" instead of transparent):
`ZoneOverlayWindow` used `Form.TransparencyKey` (chroma-key transparency) — this only makes the *exact* key color (black) invisible; any other color, even one drawn with `Color.FromArgb(lowAlpha, ...)` in GDI+, gets flattened to a fully **opaque** pixel before the window compositor ever sees it. So the "translucent" zone fills were actually rendering as solid, opaque blocks over whatever window was being dragged.

Fix:
Rewrote `ZoneOverlayWindow` to use a real layered window with per-pixel alpha (`WS_EX_LAYERED` + `UpdateLayeredWindow`, drawing into a `PixelFormat.Format32bppPArgb` bitmap) — the standard, documented Windows technique for genuinely translucent overlays (OSDs, tooltips), independent of any specific tool. Also lowered the alpha values themselves (non-highlighted zone fill 45→16, border 160→110/1.6px→1.2px; highlighted fill 120→80) so idle zones are barely-there and only the actively-highlighted one stands out.

## v1.9.11 — wallpaper startup black-flash fix (2026-10-21, same session)
User sent a screen recording showing a brief full-screen black flash the first time the animated wallpaper (Weather mode, but applies to Waves/Particles too) appears, right after Opsis starts — "ΤΟ FLICKER ΣΤΗΝ ΟΘΟΝΗ ΜΕ ΤΟ ΚΙΝΟΥΜΕΝΟ ΦΟΝΤΟ". Confirmed and pinpointed the exact bug frames by extracting the video at 15fps and building a contact-sheet montage (ffmpeg `tile` filter) — found 2-3 solid-black frames between the static desktop wallpaper and the Weather scene appearing, covering the WHOLE desktop (icons included), not just the wallpaper window's own area.

Cause:
`WallpaperWindow` already had careful "never Show() until content ready" logic (`RevealWhenReady`/`MarkContentReady`, added in an earlier pass specifically to avoid an earlier version of this same class of bug). But the WebView2 child control itself was never held back — it was `Visible=true` (WinForms default) from the moment it was created, long before the parent Form's first `Show()`. When the parent Form became visible for the first time, there was a race between the parent's own `BackColor`-erase paint (pure black) and the already-"visible" WebView2 child's surface actually getting composited on top by DWM — losing that race for a frame or two is what produced the flash. (Could not use the more surgical, Microsoft-documented `CoreWebView2Controller.IsVisible` pre-buffering technique — the installed `Microsoft.Web.WebView2` WinForms package version, 1.0.2903.40, does not expose a public `Controller` property on the WinForms `WebView2` control.)

Fix:
1. `_webView.Visible = false` set right after creation (`InitializeWebViewAsync`), kept false until reveal.
2. New `ShowRevealed()` helper sets `_webView.Visible = true` AND calls `Show()`/`SendToBack()`/`Revealed?.Invoke()` together, in the same method — replaces 3 separate call sites that previously called `Show(); SendToBack();` directly.
3. `Form.BackColor` and `WebView2.DefaultBackgroundColor` changed from pure black (`Color.Black`) to `Color.FromArgb(5,7,13)` — the exact same dark navy as `index.html`'s own CSS `background: #05070d` — as a second layer of mitigation: even if a borderline frame still slips through under different timing/hardware, it's now visually indistinguishable from the real scene instead of a stark black flash.

Affected files:
`src/Widgets/WallpaperWindow.cs` (`InitializeWebViewAsync`, `RevealWhenReady`, `MarkContentReady`, new `ShowRevealed`, constructor).

Prevention:
When a Form hosts a child control with its own independent compositing surface (WebView2, and likely any other browser-engine control), hiding the PARENT Form alone is not enough to guarantee nothing paints before content is ready — the child control's own `Visible` (or native `Controller.IsVisible` where available) must be held back and revealed in the exact same step as the parent.

Status: **DONE, LIVE-VERIFIED** (2026-10-21) — reproduced the original bug from the user's video via frame-by-frame ffmpeg contact-sheet analysis, then recorded a fresh startup of the fixed dev build the same way: zero black frames in the transition, icons and the static wallpaper stay visible right up until the Weather scene fades in smoothly. Version bumped 1.9.10 → 1.9.11, `VersionNotes.1.9.11` added (EN/EL), installer rebuilt (`Output\OpsisSetup.exe`) and installed over the user's existing `C:\Program Files\Opsis - Desktop Customization\` install.

## v1.9.12 — DeskStrip rework, License dialog fix, Quick Settings encoding fix (2026-10-21, same session)
User reported, in rapid succession, that DeskStrip (the floating app-pin dock, `src/Widgets/DeskStripWindow.cs`) doesn't resize smoothly when pinning apps, drag&drop doesn't work, there aren't enough visual effects/icon animations "like other apps" (naming SeelenUI), and it should start pre-filled with the real Windows taskbar's pinned apps. **DeskStrip rework** (`DeskStripWindow.cs` full rewrite, new `src/Services/TaskbarPinsReader.cs`):
- **Smooth resize**: `RepositionToBottomCenter` now animates Width/X together via the same ease-out-cubic Timer pattern already proven by `DeskContainerWindow`'s roll-up animation (20→16 steps/10ms), instead of snapping instantly. The very first placement on construction is NOT animated (`animate: false`), only later pin/unpin changes are.
- **Drag & drop actually fixed**: root cause was that only the empty `_tray`/Form area had `AllowDrop=true` — once a few apps are pinned, the tiles cover almost the whole bar, leaving nowhere to actually drop onto. Each `DockTile` now has `AllowDrop=true` and its own `DragEnter`/`DragDrop`, accepting both external file drops (pin) and a custom "reorder" drag format.
- **Drag-to-reorder added**: dragging one tile onto another (`MouseDown`+`MouseMove` past `SystemInformation.DragSize` threshold → `DoDragDrop` with a custom `"application/x-opsis-deskstrip-tile"` format) moves it to just before the target. **LIVE-VERIFIED**: dragged the File Explorer tile onto Chrome, confirmed via screenshot it landed directly before Chrome.

- **Taskbar pre-fill** (`TaskbarPinsReader.GetPinnedAppPaths`): on first run (no `deskstrip/config.json` yet), seeds `_paths` from the `.lnk` files in `%AppData%\Microsoft\Internet Explorer\Quick Launch\User Pinned\TaskBar` — the classic, still-functional mechanism for Win32 taskbar pins (Microsoft Store/UWP pins aren't covered, no `.lnk` there). **Real bug found and fixed within the same round, live, before shipping**: the first version resolved each `.lnk` down to its target `.exe` path (via late-bound `WScript.Shell` COM) for dedup/display — this silently dropped "File Explorer.lnk" (its `TargetPath` resolves empty, a special shell path not a plain exe) and merged a site-specific-browser shortcut ("Okairos.lnk", which happens to also target `firefox.exe`) into the real Firefox entry, hiding one and making `Icon.ExtractAssociatedIcon` show a broken/wrong icon for the exe-resolved path in another case. Fixed by keeping the `.lnk` paths themselves as the pinned "app" paths instead of resolving — `Icon.ExtractAssociatedIcon` and `Process.Start(UseShellExecute:true)` both already handle `.lnk` files correctly (own icon, own arguments), exactly like double-clicking the shortcut. **LIVE-VERIFIED**: all 7 real taskbar pins now show with correct, distinct icons (confirmed via screenshot after clearing `deskstrip/config.json` to re-trigger first-run seeding, then restoring the original `{"Paths":[]}` afterward — the user's real DeskStrip config was already empty, so no data was at risk).

**License dialog fix** (`MainWindow.cs`, `ShowLicenseDialog`): the header icon ("⚖", U+2696) doesn't reliably exist in Segoe UI and falls back to a font with unpredictable measured width — with `AutoSize=true` this made the "MIT License" title (positioned at a hardcoded X assuming a narrow icon) start overlapping the icon. **Quick Settings encoding fix** (`src/Services/SystemControlService.cs`, `GetPowerPlans`): power-plan names (e.g. "Εξισορρόπηση") rendered as mojibake in the Quick Settings widget on Greek Windows. Root cause: `powercfg /list`'s console output is written in the system OEM codepage (737 for Greek), but `Process.StandardOutput` without an explicit `StandardOutputEncoding` doesn't match that. First fix attempt (`CultureInfo.CurrentCulture.TextInfo.OEMCodePage`) was live-verified WRONG (still garbled) — a WinForms process's `CurrentCulture` doesn't reliably reflect the system locale. Root-caused by writing a standalone throwaway `dotnet run` console app reproducing the exact code path outside the full app, confirming both the exception and the fix. Final fix: `Encoding.RegisterProvider(CodePagesEncodingProvider.Instance)` added once at startup (`Program.cs`), combined with `GetOEMCP()`. **LIVE-VERIFIED**: Quick Settings widget screenshot confirms correct Greek text ("Εξισορρόπηση", "Υψηλές επιδόσεις", "Εξοικονόμηση ενέργειας") after the fix, matching the standalone test's output exactly.
